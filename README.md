# 儲備管家 (Pantry Keeper)

https://gabrielsun77.github.io/pantry-keeper/

個人食材庫存與防災儲備管理工具。純靜態網頁（PWA），沒有後端、沒有帳號，資料只存在你自己的手機／瀏覽器裡。
可以放在 GitHub Pages 上，用手機開啟後「加入主畫面」，就能像 App 一樣離線使用。

## 它會幫你做什麼

- **效期輪替（Rolling Stock）**：每個食材反推「最晚開始吃」的日期，長效期的儲備品會被均攤到效期前的每一天慢慢輪替，而不是等快過期才一次吃完。
- **今天該吃什麼**：依每類「每日上限」與「同時開封上限」排出每日菜單，已開封的優先、來不及的優先。
- **開封後另計效期**：罐頭開了 2 天、餅乾開了 10 天要吃完（各類可設），開封後截止日會取代原效期。
- **儲備健康度**：只計算「可直接吃（無火無電）」且未過期的食材，換算成一個人可以撐幾天，並和目標（預設 7 天）比較。
- **採買建議**：哪一類補幾份（含 14 天內輪替吃掉後會不足的「先買再吃」）、哪一類已超量該暫停採買、效期是否過度集中。
- **進度落後偵測**：從你登記的實際消耗算出真實速率，照這速度吃不完就提醒。
- **賞味期限寬限**：罐頭、飲料等可設過期後的寬限天數，標為「寬限中」而不是直接判死刑（可在設定改為一律嚴格）。
- **防災小物檢查表**、**匯出／匯入備份**、**匯出 CSV**。

## 部署到 GitHub Pages

1. 在 GitHub 建一個新 repository（例如 `pantry-keeper`），公開或私有皆可（私有 repo 的 Pages 需要付費方案）。
2. 把這個資料夾的所有檔案上傳到 repo 根目錄（`index.html`、`sw.js`、`manifest.webmanifest`、`icons/`、`.nojekyll`、`README.md`）。
3. 到 repo 的 **Settings → Pages**，Source 選 **Deploy from a branch**，Branch 選 `main` / `(root)`，儲存。
4. 一兩分鐘後網址會是 `https://<你的帳號>.github.io/pantry-keeper/`。

用 git 指令的話：

```bash
git init
git add .
git commit -m "儲備管家 v0.1.0"
git branch -M main
git remote add origin https://github.com/<你的帳號>/pantry-keeper.git
git push -u origin main
```

之後要更新，只要改檔案再 push，手機重開 App 時會自動抓新版（service worker 採網路優先）。
若改了 `sw.js` 快取內容，記得把裡面的 `CACHE` 版本字串一起改。

## 安裝到手機

- **iPhone (Safari)**：開啟網址 → 底部「分享」→「加入主畫面」。
- **Android (Chrome)**：開啟網址 → 右上選單 →「安裝應用程式」或「加到主畫面」。

安裝後從主畫面開啟會是全螢幕、沒有網址列，離線也能用。

## 資料與備份

- 所有資料存在該裝置瀏覽器的 localStorage，**不會同步到其他裝置**，也不會上傳到任何地方。
- 換手機、清除瀏覽器資料、或刪除主畫面 App 之前，請先到 **設定 → 匯出備份 (JSON)**，之後用「匯入備份」還原。
- 若想在電腦上分析，可用「匯出庫存 CSV」。

## 每週提醒

純靜態網頁沒有辦法在你沒開 App 時主動推播通知（iOS 對這類 App 的背景通知限制很多）。
建議在手機行事曆設一個**每週一早上**的重複提醒，打開 App 看「今天該吃什麼」和「採買清單」。
如果之後想要真正的自動推播或多裝置同步，需要加一個小後端，那會是下一版的事。

## 主要參數（設定頁都能改）

| 參數 | 預設 | 說明 |
|---|---|---|
| 人數 / 天數 | 1 / 7 | 儲備目標 = 每日需求 × 人數 × 天數 |
| 緩衝天數 | 7 | 最晚開始日再往前提早的天數 |
| 實際速率計算天數 | 14 | 用最近幾天的登記算實際消耗速率 |
| 超量門檻 | 1.5 倍 | 庫存超過目標 × 倍數且效期內吃不完 → 暫停採買 |
| 排程模擬天數 | 180 | 往後模擬多少天的菜單 |

預設類別（每日需求／每日上限／同時開封／開封後天數／寬限）：

| 類別 | 需求 | 上限 | 同時開封 | 開封後 | 寬限 |
|---|---|---|---|---|---|
| 即食主食 | 3 份 | 3 | 1 | 10 天 | 0 |
| 蛋白質罐頭 | 1.5 罐 | 1 | 1 | 2 天 | 30 天 |
| 蔬果 | 1 份 | 1 | 1 | 3 天 | 30 天 |
| 飲料/電解質 | 1 瓶 | 2 | 1 | 1 天 | 30 天 |
| 零食/糖分 | 1 份 | 2 | 1 | 10 天 | 0 |
| 其他 | 0（不計入儲備） | 2 | 1 | 3 天 | 0 |

飲用水不在此工具管理範圍內（另外管）。

## 排程邏輯簡述

1. 每個食材：`剩餘份數 = 未開封包數 × 每包份數 + 開封中剩餘`；`最晚開始日 = 效期 − 緩衝 − ceil(剩餘 ÷ 每日速率)`。
2. 從今天起逐日模擬：每類每天有「每日上限」與「同時開封上限」。
3. 已開封的食材最優先（依開封截止日），其餘依「距最晚開始日的餘裕（slack）」由小到大排。
4. slack ≤ 0 的視為急件，立刻消耗；其餘以 `剩餘 ÷ (距效期天數 − 緩衝)` 的速率累積「額度」，額度滿 1 份且有開封名額才開新包，達到均攤輪替。
5. 過了效期還有剩、或開封後超過期限沒吃完的，記為浪費並在首頁警示。
